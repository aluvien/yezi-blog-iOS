# Yezi iOS · 想法优先的创作体验

状态：2026-10-03 已按此基线实施；GPT-6.1 Sol 完成代码，主代理完成监督、原生截图复查和58项独立复测。未验证的真机与交互边界见 `implementation-review.md`。

## 1. 产品目标与本次交付

把当前以管理列表为中心的 App 改成随时记录与发布的个人创作工具。优先级：想法 > 文章 > 草稿 > 其他管理。保留现有登录、多站点、评论、附件、作品、引用、设置及部署入口。

本次需要交付可运行的原生 iOS 17+ 实现，覆盖导航、想法信息流、想法编辑器、图片流程、音乐选择、文章写作、本机草稿和异常恢复；配套回归测试、模拟器视觉验收及新版使用说明。不要只提交设计稿或静态占位 UI。

核心结果：
- 登录后的默认页是想法，单次点击进入输入；不要求标题、分类、Slug。
- 从想法首页可直接以文字、照片或音乐意图开始创作。
- 文本、图片、音乐可以任意组合；纯图片可发布。发送前清楚知道哪些图片已准备好。
- 离开、切后台、断网、上传失败不能静默丢失输入。恢复的是确实落盘的草稿。
- 写文章时正文是主体；Slug、分类、标签、封面放到发布设置中。

## 2. 现状与接口边界

当前管理壳和编辑器集中于 `YeziApp/Views/RootContentView.swift`，5 个底部入口中想法排第三；字体普遍 11–13pt；单图串行上传；音乐插入依赖 QQ 搜索和 Markdown 标记；想法发布按钮位于被上层隐藏的系统导航栏，有可达性风险。

复用 `AdminAPIClient`，不改网站数据协议，不修改网站仓库。
- 想法：`POST/PATCH /api/admin/v1/moments`，`content: String, images: [String]`，最多 9 张图片，正文最多 20,000 字符。网站仓库 `src/lib/admin/moments.ts` 已确认允许空文字加至少一张图片；不插入“分享图片”等假文案。
- 上传：`POST /api/admin/upload`，当前服务端上限 25 MiB；沿用 Cookie、Origin、CSRF 头。
- 音乐：沿用 QQ 搜索、精确 MID 播放信息、歌单接口和现有 `MarkdownParser.makeMusicSpec`；不得把搜索第一首当精确歌曲。
- 文章：创建成功保存返回 ID；再保存走 PATCH；发布必须有正文；原有引用和附件不丢失。
- 本地草稿明确是“本机草稿”，不是服务器草稿，也不是后台自动发布队列。
- 未确认服务器幂等能力前，不自动重试可能已经成功的创建请求。

## 3. 信息架构

底部 4 个入口，使用系统 TabView 或稳定的安全区内导航，保留每个 tab 的导航状态：

| 入口 | 顺序 | 首屏主要任务 | 内容 |
|---|---:|---|---|
| 想法 | 1，默认 | 写一条想法 | 记录入口、最近本机草稿提示、想法信息流 |
| 文章 | 2 | 继续写文章 | 全部/草稿/已发布，文章卡片，新建文章 |
| 草稿 | 3 | 找回未完成内容 | 本机想法和文章草稿，更新时间、附件数、站点隔离 |
| 管理 | 4 | 低频管理 | 原概览、评论、作品、附件、引用、分类标签、设置、部署 |

管理功能可移位，不能消失。原来的“内容”改成明确的“文章”。想法和文章编辑器使用有独立可见顶栏的全屏编辑界面；不依赖被父级隐藏的导航工具栏。关闭编辑器回到原来的 tab 和滚动位置。

品牌沿用叶绿色，不改为渐变科技面板。内容比装饰重要；减少英文 overline、统计卡、密集边框、微小字号。

## 5. 想法首页

顶栏：左侧“想法”，下方简短“把此刻留下。”，右侧可访问的草稿入口/状态；不放大仪表盘数字。

首屏记录区：一句“此刻，想记下什么？”的轻量入口，点击直接进入并聚焦文字；下排明确文字标签“照片”“音乐”。首页右下方安全区内保留绿色“＋ 写想法”主入口，适合长列表时单手唤起；不得遮挡最后一条内容或 tab。

有未完成想法时，记录区下方出现“继续上次记录”一行：真实文本摘要、更新时间、图片/音乐标记。没有则不占位。

信息流展示真实内容，不再把 Markdown 标记压成一行管理摘要：
- 时间使用相对日期或本地日期，小字号清晰；卡片右上“…”包含编辑、复制文字、删除（删除需确认）。
- 正文 16–17pt，默认最多约 6 行，长内容可展开或进入阅读详情。
- 单图 16:10/自然比例，限制过高；2 图双列；3–9 图三列，4 图可 2×2。裁切只发生在缩略图，点击看大图。
- 音乐显示封面、歌曲/歌单名、歌手、播放图标；不能露出 qqvip 代码。没有播放资源显示真实不可试听状态，内容仍能阅读。
- 纯图、纯音乐、长文字、图片＋音乐均有正常布局。重复图片路径仍以稳定项目 ID 展示，不触发 SwiftUI 重复 ID。
- 支持下拉刷新、分页加载状态、失败重试、初次空状态。加载失败不是“还没有想法”。

## 6. 想法编辑器

从文字入口进入后可直接打字；从照片或音乐入口进入后直接打开对应选择器，再回到同一个草稿。已有未完成新想法优先继续，不能悄悄覆盖别的草稿。

布局（由上到下）：
1. 固定 44–52pt 顶栏：关闭、居中“写想法/编辑想法”、右侧“发布/保存修改”绿色胶囊。
2. 次级状态：本机保存状态；有内容时显示“已保存到本机”，写盘失败明确提示，不假报成功。
3. 无边框正文 TextEditor：17pt，可空白，placeholder“这一刻，想说点什么…”，可自然增长/滚动。
4. 图片网格：本地缩略图先显示，逐张展示处理/上传/失败状态、删除、重试、调整顺序。
5. 音乐卡片：封面、标题、作者，试听、替换、移除。卡片属于当前草稿。
6. 底部媒体条：`照片`、`拍照`、`音乐`、`更多`。更多容纳视频、引用、Markdown 预览；低频格式功能不占首屏一整排英文字母。

提交资格：文字非空 OR 至少一张已上传图片 OR 有可序列化音乐；不得只按纯文字判断。文字超过上限、仍有待处理/上传图片、存在失败图片时不能提交；说明具体原因，例如“还有 2 张图片待上传”，并能直接重试或移除。提交中只允许一个请求，禁用重复点击和影响快照的编辑。

成功：确认服务端返回有效对象后清理对应本机草稿、轻触觉反馈，返回信息流并刷新/插入结果，显示短暂“已发布”。失败：保留全文、图片、音乐、错误和可操作入口；绝不自动关闭。

关闭行为：有改动先确保保存本机草稿，再关闭；删除输入是单独的“舍弃草稿”破坏性操作并确认。正在发送时禁止交互式关闭，允许看到提交状态。App 切后台只保存草稿，不在后台偷偷发布。发生 POST 超时/响应不可确认时，保留草稿并标记“发布结果待确认”，优先引导查看列表，不自动重发。

## 7. 图片完整流程

- PhotosPicker 一次最多选 9 张，实际可选数量 = 9 − 当前图片数量（包括本地等待项），按用户选择顺序排列。选择结束立即形成占位，不能等整批上传完再显示。
- 相机使用系统相机，权限文案清晰；模拟器/无相机设备提供解释，不崩溃。摄像权限只在点击“拍照”后请求。
- 图片处理在后台执行：ImageIO 方向校正＋缩略图下采样，通常最长边 2048、JPEG 约 0.82；不要先全尺寸解码大照片到主线程。明确格式策略，透明图保持透明或给出处理说明；文件必须低于接口上限。
- 每张图有稳定 UUID、本地文件、顺序、远端路径、状态。上传并发最多 2；取消/移除后晚到回调不得重新插入。
- 状态：准备中 → 待上传 → 上传中 → 已上传；失败 → 重试（复用本地文件）。没有真实字节进度时使用 spinner＋“上传中”，不造百分比。
- 重试仅重传失败项，不重复上传已成功项。可通过拖放和/或明确的前移、后移菜单调整顺序，发布顺序严格一致；至少有无障碍可操作的移动方式。
- 点缩略图可大图预览；返回不影响输入、选择和顺序。
- 原始/处理后的草稿图片存放 App 自有 Application Support 子目录，采用适当文件保护；JSON 原子写盘；路径使用受控相对文件名，不能从远端反序列化任意磁盘路径。
- 本地缩略图与远端图片分开；重启恢复后上传已成功的图片不重传。本地文件不存在时明确显示失败项供移除或重新选择，不能静默删掉。
- 不删除服务器附件以“撤销上传”；它们可能已经被其他内容引用。仅清理本草稿所有的本地文件。

## 8. 音乐完整流程

独立 sheet，标题“添加音乐”，可扩展高度；默认歌曲，切换“歌曲/歌单”；搜索框支持键盘搜索与 300ms 左右防抖。清空查询、切换类型、关闭时取消旧查询，用 generation 保证旧结果不能覆盖新结果。

未查询时显示按当前站点隔离的“最近添加”（最多 10 条，真实数据，不虚构热门榜），并提供折叠的“粘贴链接或手动输入”。支持现有 qqvip 格式；只转换明确识别的 QQ 完整链接，不猜测短链接或其他平台 ID。输入无效给出示例。

结果行：48pt 封面、歌曲名/作者/专辑、独立试听按钮、选择标记。选中后底部主按钮“添加这首音乐”；选择歌单时显示歌单信息，随机播放选项仅对歌单有效。

试听使用精确 MID 信息与 AVPlayer；切换曲目、关闭 sheet、切后台、移除卡片时停止旧音频。不可播放不等于不可添加：显示“暂不能试听”，仍允许添加合法音乐。

新增想法通常一张音乐卡，替换需要明确动作；编辑包含多条旧音乐标记的想法时必须保留全部，不得只读第一条后丢掉其余。解析/拆分不能破坏未识别 Markdown 或引用标记。想法保存使用 `!music qqvip:…` 行标记；可选 `:fold` 与网站一致地折叠展示，歌单随机播放保留 `:random`。元数据快照在网站允许的规格长度内保留；编辑时兼容旧 fenced music/qqvip 格式。

## 9. 文章体验

文章首页：标题“文章”，分段“全部/草稿/已发布”，卡片突出标题、两行摘要、封面与状态；主入口“写文章”。列表计数失败不能阻止内容展示。已有管理搜索可保留，不展示假全站搜索。

文章编辑：独立可见顶栏，关闭、状态、`发布/更新文章`；主画布是 26–28pt 标题和 17pt 正文；底部包含照片、音乐、格式、预览。Markdown 格式操作有可理解的中文/图标名称，不要求用户理解 B/I/P/M/V。

发布设置 sheet：封面、Slug、分类、标签、关联附件、引用信息。新文章 Slug 可自动生成安全唯一候选，并允许手动修改；不要强迫用户先手写。已有 Slug 不擅自改动。

本机保存覆盖新建与已发表文章的未提交编辑。服务端“保存草稿”为显式操作：新文章创建成功保存 ID，后续保存 PATCH；已发表文章不得因自动保存变草稿。若提供“转为草稿”，确认其会从网站隐藏。

修复审计相关问题：
- 自动保存不取消正在进行的写入；用 revision/dirty 状态串行补存，或以可靠本机保存替代隐式服务器写入。
- `AdminPostDetail` 对编辑必需字段严格解码，缺失 content/id/title/slug/status 时拒绝，不用空值掩盖损坏响应。
- `decodeEnvelope` 明确区分直接对象与封装格式，避免全 optional envelope 吞掉直接对象；分页别名与真实解码器策略一致。
- 保存失败不关闭；图片处理中不得发布不完整快照；发布成功才清理该草稿。

## 10. 本机草稿

统一 DraftStore，以 canonical site origin（scheme/host/port）隔离；类型 moment/post；record ID、server ID（如有）、createdAt、updatedAt、revision、text/metadata、media refs、submit 状态。不得存密码或 Cookie。

保存防抖约 300–500ms，离开与 scenePhase inactive/background 时 flush 最新快照。文件原子写入并串行处理，旧写入不得覆盖新版本。读取损坏文件保留可恢复数据并明确反馈，不自动全盘删除。

草稿页分“想法/文章”，显示摘要、修改时间、附件数量，点开恢复。删除先确认；切换站点看不到其他站点草稿，但切回仍可恢复。编辑现有服务器内容先加载并确认身份，再合并该记录的本机草稿；不能在加载失败时自动提交空值。

## 11. 状态文案与无障碍

| 场景 | 文案/动作 |
|---|---|
| 正常输入 | 已保存到本机 / 正在保存… |
| 写盘失败 | 暂未保存，请保持此页并重试 |
| 上传中 | 正在上传 2 张图片 |
| 单图失败 | 上传失败 · 点按重试 |
| 无网络 | 暂时离线，内容已保存在本机（仅落盘成功才这样说） |
| 提交确定失败 | 发布失败，内容已保留 · 重试 |
| 提交结果不确定 | 发布结果待确认 · 查看想法 |
| 音乐无结果 | 没找到这首音乐，试试歌曲名或歌手 |
| 音乐服务失败 | 音乐服务暂不可用 · 重试 / 手动添加 |
| 登录过期 | 需要重新登录，已保留本机草稿 |

图片按钮具有“移除第 2 张图片”“重试第 2 张图片”等标签；音乐试听与选择分开；状态不能仅靠颜色；尊重 Reduce Motion；支持深色、VoiceOver、动态字号；发布按钮 disabled 时旁边或状态栏能读到原因。

## 12. 实施拆分与所有权

主代理负责 `docs/design/` 内设计、可点击视觉样稿、验收记录；执行者不得自行改变设计基线。执行者独占 `YeziApp/`、`YeziAppTests/`、Xcode project/scheme 与 README 的本次源码写入，避免并行写同一文件。

建议新增分离模块：CreationDesign、CreationDraftStore、MediaUploadQueue、MomentComposerModel/View、MomentFeedView、MusicPickerModel/View、ArticleComposer、LocalDraftsView；可按实际复用调整命名。RootContentView 只做路由连接，不要继续堆入几千行新编辑代码。新增源文件必须加入显式 PBX project 编译列表。

执行者是用户明确指定的 GPT-6.1 Sol，父代理当前实际模型为 GPT-6 Astra，任务模型上限 Astra。子任务不再转派、不升级模型、不提交/推送、不访问线上写接口做测试。先 High 执行；若代码/验证失败，主代理可给一次 XHigh 修复机会，再由主代理收尾。

执行阶段：
1. 基础状态、草稿存储和 API 修复；先有有意义的失败/恢复测试。
2. 想法优先壳、信息流、编辑器及图片与音乐；逐个入口可以完整闭环。
3. 文章、草稿入口及旧功能接入；更新 README。
4. 模拟器与测试验收；有失败项继续修复，不能以“可后续完善”替代本次明确范围。
